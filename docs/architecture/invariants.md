# Invariants

Rules that must always hold. Each row names the mechanism that enforces it.
"Review" in the *Enforced by* cell means no mechanism exists yet; such a row
must cite the issue that will replace it with one.

Add a row in the pull request that introduces the rule or its enforcement.
Removing a row needs an ADR. Numbers are never reused: I-5 and I-11 belonged
to the group-tree design and were withdrawn by ADR 0004; I-2 was restated
when cross-organisation sharing left the v1 design (ADR 0007).

| # | Invariant | Enforced by |
|---|---|---|
| I-1 | Tenant-owned data never crosses the organisation boundary: every SELECT, UPDATE and DELETE on an organisation-owned table is scoped by `organization_id`, and every INSERT stores the correct `organization_id` explicitly. No exceptions; channels and everything under them included. | Planned: source test over the database package — SELECT/UPDATE/DELETE without the predicate, or INSERT without the column, fails unless allow-listed with a reason |
| I-2 | Channel content (members, topics, messages, attachments, reactions, read state) is readable and writable only by members of that channel, in addition to I-1. The single, deliberate exception: a user of the same organisation may create **their own** membership in a **public** channel (self-join). No other membership operation is available to a non-member. | Planned: route-table sweep (non-member → 404 on every channel-scoped route, except self-join on a public channel → 201; self-join on a private channel → 404; joining someone else → 404); source test that channel-content queries join on membership |
| I-3 | Access decisions ask for a capability, never a role name. For users, the only non-capability grant is `channel_member.is_admin`, consulted solely by actions that explicitly permit a channel admin. Bots hold no roles or capabilities; what they may do is a fixed, narrow set (ADR 0012). | Planned: source test — no comparison against role names outside the role package |
| I-4 | Reachability (`canReach(a, b)`: share a channel, or `a` holds `view_directory`) is computed in exactly one place, between users only. Only the `view_directory` capability grants visibility beyond shared channels. Action policies call it; nothing else computes visibility. | Planned: source test — the reachability query exists in one package; policies import it; integration test over the two clauses and their absence |
| I-6 | **TODO — not yet settled.** DM policies (starting a DM, posting to an existing DM, adding a participant to a group DM, per-user exceptions) are per-action policies that combine reachability with the capabilities of both people and organisation settings; reachability alone never permits a DM. The rules are open in ADR 0005, expressed as user stories rather than organisation-chart relationships. | To be defined with the authorisation issue; until then: Review |
| I-7 | Channel invitation requires **both**: (1) the inviter can reach the target; and (2) the inviter either holds the organisation-wide invite capability or is an admin (`is_admin`) of that channel. | Planned: route-table sweep cases (unreachable target → 404; inviter without the capability for this channel → 403, including an admin of a different channel) |
| I-8 | A message's id is stable across topic moves. | Planned: integration test on the move operation |
| I-9 | Creating a topic from a reply, moving the original message and inserting the reply happen in one transaction. | Planned: integration test that injects a failure after the move and asserts full rollback |
| I-10 | A topic is never moved to a channel of a different organisation (I-1 restated for the move operation). | Planned: integration test + route-table sweep case |
| I-12 | Audit records are append-only: never updated or deleted, not even to fix a mistake. A correction is a new audit record that refers to the one it corrects. | Planned: the application's database role has no UPDATE/DELETE on the table; a test proves the grant; no application code path exposes an update |
| I-13 | Message bodies, password hashes, session tokens, API tokens, invite/login links, email addresses and usernames are never logged; the internal `actor_id` is the only identifier for a person or bot in logs. | Planned: log through a wrapper with typed fields; source test forbids raw `slog` calls outside the logging package; sensitive types implement `LogValue` that redacts |
| I-14 | Application SQL lives only in the designated database package; migrations are the exception. | Planned: source test over `*.go` for SQL keywords outside the package |
| I-15 | `panic` only for bugs and start-up preconditions; never for expected failures. No `os.Exit` outside `main`. | Planned: `forbidigo` on `panic(` and `os.Exit` in production code, exceptions via `//nolint` with a reason (`nolintlint`); a recover middleware with a test |
| I-16 | Commits on `main` arrive only through a merged pull request. | GitHub branch protection (pull request + green CI required, no force push) + `.githooks` locally |
| I-17 | Every commit carries a DCO sign-off. | CI (`dco.yml`) |
| I-18 | Tests and lints are never weakened to pass: no `t.Skip` without an issue link, no `//nolint` without a reason. Coverage percentage is reported as information and is never a gate; what is gated is that the pull request names the behaviours, boundary conditions and must-not-break points it tested. | Planned: `nolintlint`; source test on `t.Skip`; diff coverage posted as a comment; CI fails on an empty "what was tested" section in the pull request; optional manually triggered mutation-testing job for information |
| I-19 | Generated code (`sqlc`, `oapi-codegen`, the TypeScript client, and any later generator) is never edited by hand; only its source and configuration change. | Planned: CI runs every generator and fails on a non-empty `git diff`; generated files carry a header and are listed in `.gitattributes` as `linguist-generated` |
| I-20 | Every HTTP route is registered in the route table with its **allowed authentication modes** (one or more of `session`, `token`, `webhook`; a `/api/v1` endpoint may accept both `session` and `token`) or with `public`, which stands alone and is never combined with another mode; a route registered elsewhere does not exist; the SPA calls only `/api/v1`. | Planned: source test rejects route registration outside the table and rejects `public` combined with another mode; the sweep exercises the rejection cases for every mode a route does *not* allow and the credential-failure cases for each it does; the front end's generated client covers every call it makes |
| I-21 | Authorship, membership and audit reference `actor`, never `user`; an API token belongs to exactly one actor and is stored hashed. | Planned: schema (foreign keys to `actor` only; no `user_id` on those tables) + source test on migrations; token storage test |
| I-22 | A bot never holds directory visibility and is outside reachability; it joins a channel only through `canInstallBot`. | Planned: unit test that reachability is defined over users only and `canInstallBot` is the sole path to bot membership; route-table sweep case |
| I-23 | Every actor — human user or bot — belongs to exactly one organisation: `organization_id` is required on `actor`, and it never changes after creation. Acting in another organisation requires a different actor. The chain `token → actor → organization` therefore always resolves to exactly one organisation, which is what makes the actor a safe common principal for token ownership, authorship, channel membership and audit identity. | Planned: `NOT NULL` on `actor.organization_id`; no UPDATE path for the column (trigger or database grant, plus a test); the authentication layer derives the organisation from the actor, never from the request |
